
# Book Snippet Policy

## Rule

All Mist code examples in the book MUST be checked-in snippet files that compile successfully. Never use inline Mist code blocks in the markdown — always use `{{#include}}` references to files in `book/snippets/`.

## Snippet Structure

Each snippet is a complete, compilable Mist program stored at:

```
book/snippets/<section>/<chapter>/<snippet-name>.mist
```

Every `.mist` snippet MUST have a corresponding `.cs` file containing the actual compiler output:

```
book/snippets/<section>/<chapter>/<snippet-name>.cs
```

## Generating the Emitted C#

The `.cs` file MUST be generated by the SnippetEmitter tool — never hand-written. After creating or
modifying a snippet, regenerate only the affected examples. Run commands from the repository root.

One example:

```bash
dotnet run --project tools/SnippetEmitter -- book/snippets/getting-started/hello-world.mist
```

Several examples, or a chapter (directories are searched recursively):

```bash
dotnet run --project tools/SnippetEmitter -- book/snippets/basics/functions/static-methods.mist book/snippets/getting-started/hello-world.mist
dotnet run --project tools/SnippetEmitter -- book/snippets/basics/functions
```

Use an existing chapter directory; a path that does not exist is an error. Add `--list` to preview
the selected pairs without compiling or writing. Overlapping selectors compile each pair once.

Each selected example still compiles with its transitive `// with:` companions, `<snippet>.support/`
files and project sidecar. Selecting one example does not regenerate the companions' own C# tabs
or other examples that depend on it. After changing a shared companion or support file, select all
affected examples explicitly or regenerate their containing chapter. A `.toml` change requires
regenerating its matching example. Directory selection includes only `.mist` files with `.cs` twins;
an explicitly selected `.mist` without a twin is an error.

Full-book regeneration is warranted when a compiler or Standard library change affects emitted
output across the book, or when deliberately refreshing every C# tab:

```bash
dotnet run --project tools/SnippetEmitter -- book/snippets
```

Omitting all paths also selects the whole book for compatibility. Do not use that form for an
ordinary snippet edit. `mdbook build book` renders the generated files; it does not regenerate them.

Generation uses a bounded pool of worker processes, each compiling its assigned examples sequentially
with a reused compiler driver. The default is half the available CPUs, capped at eight workers and
the number of selected examples. Use `--jobs 1` for a sequential run, or `--jobs N` to limit the load.
Add `--timings` for per-example compile counts and stage timings, aggregate worker time and elapsed
generation time. Elapsed generation time excludes building the tool. To exclude the build from
repeated measurements, build once, then use `dotnet run --no-build --project tools/SnippetEmitter -- ...`.
Rebuild after changing the compiler, Standard library or tool.

Every selected example goes through compilation validation, including Roslyn compilation of the
generated C#. An `unchanged` result means the newly validated output matches the existing tab; it
does not skip compilation. There is no persistent generated-output cache. The tool reports updated,
unchanged and failed counts and exits unsuccessfully if any example fails. A snippet that fails keeps
its old `.cs`, so a failure is a stale tab until the snippet is fixed; track any unresolved snippet
defect in Carbonek project MIST with the failing snippet and regeneration evidence.

To add a new snippet:
1. Create the `.mist` file
2. Create an empty `.cs` file at the same path (the tool only processes pairs)
3. Run SnippetEmitter with the new `.mist` file's path to populate its `.cs` twin
4. If the tool reports a failure, the snippet doesn't compile and must be fixed

## Markdown Format

Use the tabbed include pattern for every snippet:

```markdown
{{#tabs }}
{{#tab name="Mist" }}
\```mist
{{#include ../../snippets/<section>/<chapter>/<snippet-name>.mist}}
\```
{{#endtab }}
{{#tab name="Emitted C#" }}
\```csharp
{{#include ../../snippets/<section>/<chapter>/<snippet-name>.cs}}
\```
{{#endtab }}
{{#endtabs }}
```

## Snippet Requirements

- Each `.mist` file MUST be a complete program: `using Standard;`, namespace, class with `Main`, etc.
  A snippet that needs a package or framework reference keeps a project file beside it, named as the
  snippet is (`framework-reference.toml`), which the tool uses as the scratch project's `mist.toml`.
  A snippet that builds on a sibling names it on a `// with: declaring.mist` line after the usings;
  the named files, and whatever they name in turn, are compiled alongside it and the book shows only
  the snippet. A companion must declare only: a file with a `Main` or top-level statements is a
  program of its own and cannot be one. A snippet that needs a folder layout, such as a namespace
  inferred from a folder, keeps its other files in `<snippet>.support/` instead.
- Each snippet should be small and focused — one concept per file.
- The snippet MUST compile and run without errors through the Mist CLI.
- If a feature is not yet implemented, use an inline code block with a blockquote explaining the limitation. Do NOT create a snippet file for code that doesn't compile.

## Exceptions

Inline code blocks (without `{{#include}}`) are acceptable ONLY for:

- Pseudocode or conceptual examples explicitly marked as "not Mist syntax"
- Features that are designed but not yet implemented (must be marked with a blockquote noting the limitation)
- Error message examples showing compiler diagnostics
- A declaration-only snippet the compiler emits nothing for, such as a variadic declaration with no use,
  whose C# tab is an illustration: keep it inline, name the tab `Emitted C# (illustration)`, note under
  the tabs why nothing is generated, and give the snippet no `.cs` twin so the tool does not count it

## Syntax Highlighting Sync

The book uses two files that define Mist syntax highlighting and they MUST be kept in sync:

- `book/theme/highlight.js` — The deployed file. Contains the minified hljs core with the Mist language definition appended at the end. mdBook uses this during static site generation.
- `book/theme/mist-lang.js` — The readable source. A standalone copy of just the Mist language definition for easier editing.

**When adding new keywords or modifiers to the Mist language**, you MUST update BOTH files:

1. Edit `mist-lang.js` (the readable source)
2. Update the corresponding section at the end of `highlight.js` to match exactly

The relevant variables to keep in sync are:
- `MODIFIERS` — storage modifiers like `public`, `static`, `owned`, `linear`, `affine`, `relevant` (colored orange)
- `RESERVED_TYPES` — type keywords like `int`, `string`, `var`, `void`, `func` (colored blue)
- `KEYWORDS` — language keywords like `class`, `if`, `return`, `await` (colored purple)

**Never edit one without the other.** If you add a keyword to `mist-lang.js`, you must also add it to `highlight.js`.
