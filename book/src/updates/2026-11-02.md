## Diagnostics Refactor

Compiler diagnostics now have one structure from the rule that finds a problem to the
terminal, an editor or a build tool. Each report records facts with a stable identity and
traceable origin; a shared renderer turns those facts into a readable message.

**Codes identify; categories organize.** Every diagnostic has a `MISTnnnn` code and belongs
to one of thirteen semantic categories, including syntax, types, ownership, effects and
interoperability. The digits do not encode the category or compiler stage. Moving a check
between stages therefore does not change its public identity.

**Rules report typed facts.** Named arguments retain types, symbols and paths as structured
data. Related declarations, underlying causes and native Roslyn details remain available
to tools. Locations distinguish source ranges, project files and external symbols; an
unavailable position stays explicit. Two distinct findings are not merged just because
their messages match.

**Policy and presentation are separate.** Projects can promote warnings and notes to errors
and enable or disable optional rules. Fixed errors cannot be disabled. Build success uses
effective severity; hiding a warning from terminal output does not change the result.
JSON retains filtered findings and records their visibility.

The CLI can write one versioned JSON document while keeping readable diagnostics on stderr
and the compiled program's output separate:

```bash
mist build my-project --diagnostic-file diagnostics.json
```

The [diagnostic reference](../reference/diagnostics.md) explains the categories, severity
policy, locations and JSON fields in detail. Its catalog is generated from the compiler's
registry. Registry validation and message-text checks catch duplicate codes, missing metadata
and unintended wording changes, keeping diagnostics a maintained public contract.

## General Improvements

### Infer Local Loans and Preserve Their Lifetimes

Local ownership inference now handles scoped loans from owned values. A local can borrow an
existing object for an inner scope, with the original becoming available again afterward;
mutation through that loan affects the same object. Ownership tracking also follows
conditional selections, aliases and optional views so they preserve the original value's
restrictions and cleanup obligations.

The Ownership and ResourceTransfer samples now exercise these cases in the aggregate baseline.

### C# Backend Interop: .NET Base Classes

The C# backend now provides better interop with .NET base classes: a Mist class can implement
their virtual and abstract members. Declare the matching member in Mist; the compiler
recognizes that it fills the inherited slot, and the C# backend emits `override`. Calls
through the .NET base type reach the Mist implementation too. Mist needs no `virtual` or
`override` keyword.

This makes framework extension points usable from Mist. For example, overriding
`Collection<int>.InsertItem` lets a Mist class control what happens when callers add an item,
including through a `Collection<int>` reference. The compiler checks missing abstract
implementations, sealed members and mismatched signatures. It also refuses an accidental
redeclaration of a nonvirtual CLR member instead of silently hiding it.

C# backend tests now construct their inputs directly where the behavior belongs to the emitter,

## Under Development

### Error Handling

Mist's error-handling specification is designed, committed to main and now in implementation.
It gives failures an explicit place in a function's return type, makes common propagation
concise, and lets Mist programs contain exceptions from .NET APIs. This is also a major
prerequisite for writing the compiler itself in Mist.

**Failures are ordinary values.** `Result<T, E>` contains either a successful `T` or an error
`E`. An error can be a domain type with useful fields, such as a failed input's location;
it does not have to inherit from `System.Exception`. `Result<T>` is shorthand for
`Result<T, Error>`, and `Result<void, E>` represents an operation that can fail but has no
success payload. Construction always selects a valid alternative: there is no default or
uninitialized Result state.

**Postfix `!` means succeed here or return the error.** It extracts the successful value or
returns the error from the enclosing function, whose return type must accept that error.
It performs the same required cleanup as an explicit early return. Mist gains no `throw`,
`try` or `catch` keywords, and `!` never means an unchecked unwrap that can panic.

```mist
Result<string> ReadText(string path)
{
    var text = System.Exception.Catch(System.IO.File.ReadAllText, path)!;
    return text;
}
```

Here `Catch` calls `ReadAllText` inside a generated exception boundary and returns
`Result<string, System.Exception>`. If reading fails, `!` returns that error immediately;
otherwise `text` is a string. Standard supplies compatibility between `System.Exception`
and the shared `Error` contract. Returning `text` constructs the successful Result without
repeating its full type. Where a payload could mean either success or failure, the compiler
requires an explicit choice such as `AsSuccess()` or `AsFailure()`.

**Handling an error is explicit too.** `Inspect()` exposes a tagged pair for pattern matching:

```mist
var description = result.Inspect() switch
{
    (true, var value) => Describe(value),
    (false, var error) => DescribeError(error)
};
```

The tag proves which payload is available, even when success and error have the same type.
There is no unconditional `Value` accessor. Silently discarding a Result is a compile-time
error; `_ = operation();` records an intentional decision to ignore it. Implicit cleanup
cannot quietly discard a Result-valued close failure either.

**The CLR wrapper is opt-in and general.** Pass a method and its arguments to
`System.Exception.Catch`; no separate wrapper or exception mapper is needed for every .NET
method. It retains the original exception object. The async adapter protects invocation
and task completion, producing `Task<Result<T, System.Exception>>`; cancellation caught
there is also an ordinary error Result. Arguments are evaluated before the boundary;
a lambda can move that preparation inside it. Raw CLR calls retain their foreign failure
behavior, so a Result return type alone does not make arbitrary foreign code panic-free.

**Arithmetic follows what the compiler can prove.** For integer division, a proven-safe
operation returns a number, a proven-invalid operation is a compile-time error, and an
uncertain operation returns a Result. Both division by zero and signed overflow matter.
The spelling `(x / y)!` works on either the safe or fallible route: `!` leaves a proven-safe
plain value unchanged. Existing wrapping integer addition remains wrapping.

Implementation starts with Result representation, inspection and `!`, followed by arithmetic,
CLR boundaries, handling and cleanup checks, and integration into the book and samples.

### Self Bootstrapping Mist

The goal is to write both Mist's compiler and Storm, its grammar tool, in Mist. Completion
requires a compiler that rebuilds successive generations of itself, regenerates its own
frontend, and preserves program behavior and diagnostics without falling back to the C#
seed implementation. The C# backend and .NET dependencies can remain.

This work is on the separate `self-host` branch. Its delivered foundations include source
generator hosting and caching, text and character APIs, numeric and array operations, and a
unified reflection identity for `Standard.Type` and `System.Type`. Recent fixes cover Void
property getters and inherited `IDisposable` cleanup.

A new seed acceptance harness records each sample independently so later compiler generations
can be compared against it. Its reported run has **102 passing samples, five supporting
projects exercised, and seven standalone failures** from samples with no entry point. Those
failures remain failures even when the aggregate sample passes. The latest combined delivery
also reported 13,972 repository tests passing, a warning-free build and clean formatting.

This is preparation for the port, not a self-hosted compiler yet. Error-handling implementation
is a major dependency, and the location and build/test arrangement for Mist-authored Storm
remain an owner decision.

### C# Interop: Razor

Razor support is an upcoming feature of Mist's C# backend. The goal is to write a Blazor
application with `.razor` components alongside ordinary `.mist` files, using Mist in every
code position, then build and run it with `mist build` and `mist run`. The initial scope is
components and Interactive Server hosting. A `Counter.razor` component would look like this:

```razor
@page "/counter"

<p>Count: @count</p>
@if (lastReset is void)
{
    <p>Not reset yet.</p>
}
else
{
    <p>Last reset at @lastReset.</p>
}

<button @onclick="Increment">Add one</button>
<button @onclick="Reset">Reset</button>

@code {
    private int count = 0;
    private int? lastReset = void;

    private void Increment()
    {
        count = count + 1;
    }

    private void Reset()
    {
        lastReset = count;
        count = 0;
    }
}
```

The markup displays the count and connects buttons to Mist methods. Mist's optional-value
rules apply inside the component: `int?` can hold a number or `void`, and `is void` checks
whether a reset has happened. Expressions, control flow and `@code` members all use Mist.

## In Design

### Generic Discipline & Ownership for Types

The generic discipline and ownership design has a concrete target: a standard-library
`List<T>` written in ordinary Mist, using the same facilities available to anyone writing a
container. It must account for owned elements, retained borrows, frozen and live views, and
the cleanup obligations of linear, affine and relevant values.

The current direction separates owning the container from owning its contents. A container
may own its shell while borrowing its payload. Retaining an exclusive loan suspends the
lender's access; releasing the loan restores it. Returning or moving the container must carry
those dependencies with it, and ordinary field access must preserve the field's owner.

Generic qualifier syntax, storage contracts and how a container declares or infers its own
discipline are still being worked through. This remains specification development.

### First Class Allocators & Schedulers

Memory placement and execution are being designed as values a program can define and compose.
An allocator draws storage from a parent allocator; a scheduler borrows workers from a parent
scheduler. The system supplies the roots. The intended compiler checks prevent values from
outliving their storage and tasks from racing on shared data, while each implementation
chooses its own policy and is trusted to honor its declared provider contract.

The design keeps garbage collection, a thread pool and tasks possible, while allowing other
policies. On .NET, the root scheduler remains the .NET thread pool. Allocators and schedulers
are ordinary linear values, and `with` selects which is current without making every
installation an ownership transfer.

At the supplied design checkpoint, all **17 scheduler decisions** were settled and **9 of 23
allocator decisions** were settled. Remaining questions include values that might refer to
storage released at block exit, raw allocation results, retention and foreign callbacks.
Implementation planning follows those decisions; the allocator/scheduler feature itself is
not implemented. The ownership fix for `with` blocks is already on main and is covered below.

## Bug Fixes

### Fix Double or Missing Drops in `with` Blocks

A soundness bug allowed linear and affine values to be dropped or moved while a `with`
block still depended on them. This could happen directly inside the block or in called
functions accessing the value through a structured context variable. The result could be
a double drop or a required drop never happening.

The compiler now rejects those consuming uses. While the block owns the value, neither
the original variable, an alias nor a called function's context variable can drop it or
transfer its ownership. The block remains responsible for dropping it on exit. Functions
can still read the value or use explicit loans.
