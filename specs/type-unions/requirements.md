# Requirements Document

## Introduction

This document specifies the requirements for adding type unions to the Mist programming language. Type unions allow a type annotation to express that a value may be one of several types, using the `|` operator (TypeScript-style syntax). For example, `int | string` denotes a value that is either an `int` or a `string`.

Type unions can appear anywhere a type is used: variable declarations, method parameters, method return types, type arguments, field declarations, and pattern matching contexts. The feature is split into two concerns: (1) semantic correctness within Mist's type system, and (2) C# code emission that achieves semantic equivalence even when C# lacks native union type support (C# discriminated unions are in preview but not yet stable).

The C# emission strategy prioritizes behavioral correctness over elegant C# output. The emitter may generate helper types, wrapper structs, multiple statements, or other constructs to faithfully represent Mist union semantics in the C# runtime.

Out of scope for this spec: union type narrowing via control flow analysis (beyond what pattern matching already provides), union type simplification/normalization at the type level (e.g., flattening nested unions or removing duplicates), and variance interactions with generics.

## Glossary

- **Compiler**: The Mist compiler pipeline, including lexing, parsing, semantic model construction, analysis, and C# code emission.
- **Grammar**: The Storm grammar definition that specifies the syntax of the Mist language (`Mist.storm` and `keywords.storm`).
- **Parser**: The component that reads Mist source tokens and produces an abstract syntax tree (AST) conforming to the Grammar.
- **Pretty_Printer**: The component (`MistPrettyPrinter`) that formats a Mist AST back into valid Mist source text.
- **Semantic_Model_Builder**: The component (`SemanticModelBuilder`) that constructs the semantic model from the AST in multiple passes.
- **Type_Checker**: The analysis component (`TypeCheckerAnalyzer`) that validates type rules against the semantic model.
- **Emitter**: The C# code emission component (`CSharpEmitter` / `CSharpSourceWriter`) that translates the Mist AST into C# source files.
- **Type_Union**: A composite type formed by combining two or more constituent types with the `|` operator (e.g., `int | string`). A value of a union type may hold a value of any one of its constituent types at runtime.
- **Constituent_Type**: An individual type that is a member of a Type_Union (e.g., `int` and `string` are constituent types of `int | string`).
- **Union_Type_Reference**: A syntactic type reference that uses the `|` operator to combine multiple type references into a Type_Union (e.g., `int | string | bool`).
- **UnionType**: The semantic model representation of a Type_Union, containing an ordered list of resolved Constituent_Types.
- **Type_Narrowing**: The process by which a pattern match on a union-typed value restricts the known type within a branch (e.g., after `x is string s`, `s` is known to be `string` within the then-branch).
- **Helper_Type**: A C# type generated by the Emitter to represent a Mist Type_Union at runtime, since C# does not natively support arbitrary discriminated unions.
- **PIPE**: The `|` token used as the union type operator in type reference contexts.

## Requirements

### Requirement 1: Union Type Syntax Token

**User Story:** As a Mist developer, I want the compiler to recognize the `|` character as a type union operator in type contexts, so that I can write union type annotations.

#### Acceptance Criteria

1. THE Grammar SHALL define a `PIPE` token with the value `"|"`, declared before the `LOGICAL_OR` token (`"||"`) so that maximal-munch selects `||` when two pipe characters appear consecutively.
2. WHEN the lexer encounters a single `|` character that is not part of `||`, THE lexer SHALL produce a `PIPE` token.
3. WHEN the lexer encounters `||`, THE lexer SHALL produce a `LOGICAL_OR` token, not two `PIPE` tokens.

### Requirement 2: Union Type Grammar Rule

**User Story:** As a Mist developer, I want to write type annotations using the `|` operator to combine multiple types, so that I can express that a value may be one of several types.

#### Acceptance Criteria

1. THE Grammar SHALL define a `UnionTypeRef` alternative within the `TypeReference` rule that matches two or more type references separated by the `PIPE` token (e.g., `int | string`, `int | string | bool`).
2. THE Grammar SHALL give the `PIPE` operator lower precedence than array rank notation, so that `int[] | string` is parsed as `(int[]) | string` rather than `int ([] | string)`.
3. THE Grammar SHALL support union types composed of any valid type reference as a constituent, including primitive types, named types, generic constructed types, array types, tuple types, and other union types.
4. WHEN a union type reference is parsed, THE Parser SHALL produce an AST node that captures the ordered list of constituent type references.
5. THE Grammar SHALL support parenthesized grouping within union types to allow explicit precedence (e.g., `(int | string)[]` for an array of a union type).

### Requirement 3: Union Types in All Type Positions

**User Story:** As a Mist developer, I want to use union types anywhere a type annotation is accepted, so that I can express flexible typing in variables, parameters, return types, fields, and type arguments.

#### Acceptance Criteria

1. WHEN a variable declaration uses a union type annotation (e.g., `int | string x = 42;`), THE Parser SHALL parse the union type as the variable's type.
2. WHEN a method parameter uses a union type annotation (e.g., `fun process(value: int | string): void`), THE Parser SHALL parse the union type as the parameter's type.
3. WHEN a method return type is a union type (e.g., `fun getValue(): int | string`), THE Parser SHALL parse the union type as the return type.
4. WHEN a field declaration uses a union type (e.g., `int | string data;`), THE Parser SHALL parse the union type as the field's type.
5. WHEN a type argument is a union type (e.g., `List<int | string>`), THE Parser SHALL parse the union type as the type argument.
6. WHEN a union type is used in a pattern match context (e.g., `x is int | string`), THE Grammar SHALL disambiguate between the union type operator and the pattern `or` combinator based on syntactic context.

### Requirement 4: Pretty-Printer Support for Union Types

**User Story:** As a Mist developer, I want the pretty-printer to correctly format union type annotations, so that round-trip printing preserves the source structure.

#### Acceptance Criteria

1. THE Pretty_Printer SHALL format a union type as `Type1 | Type2` with spaces around the `|` operator.
2. THE Pretty_Printer SHALL format multi-constituent union types as `Type1 | Type2 | Type3` with consistent spacing.
3. THE Pretty_Printer SHALL format union types within generic type arguments as `List<int | string>`.
4. THE Pretty_Printer SHALL format union types with array rank as `(int | string)[]` when the array applies to the entire union, and as `int[] | string` when the array applies to a single constituent.
5. FOR ALL valid Mist ASTs containing union type references, parsing then pretty-printing then parsing SHALL produce an equivalent AST (round-trip property).

### Requirement 5: Semantic Model for Union Types

**User Story:** As a Mist developer, I want the compiler to resolve union type references into a semantic union type, so that the type system can reason about values that may be one of several types.

#### Acceptance Criteria

1. WHEN a type reference contains a union type (e.g., `int | string`), THE Semantic_Model_Builder SHALL resolve it to a `UnionType` instance containing the resolved constituent types.
2. THE Semantic_Model_Builder SHALL flatten nested union types so that `(int | string) | bool` resolves to a `UnionType` with three constituents: `int`, `string`, `bool`.
3. WHEN a union type contains duplicate constituent types (e.g., `int | int`), THE Semantic_Model_Builder SHALL deduplicate them, producing a `UnionType` with distinct constituents only.
4. WHEN a union type contains a single constituent after deduplication, THE Semantic_Model_Builder SHALL reduce it to the constituent type itself (not a union).
5. WHEN a constituent type reference in a union cannot be resolved, THE Semantic_Model_Builder SHALL emit a diagnostic error for the unresolved type and use `ErrorType` for that constituent.
6. THE Semantic_Model_Builder SHALL store the `UnionType` on fields, parameters, return types, and local variables that use union type annotations.

### Requirement 6: Type Checking — Assignability Rules for Union Types

**User Story:** As a Mist developer, I want the type checker to correctly validate assignments involving union types, so that type safety is maintained when working with values that may be one of several types.

#### Acceptance Criteria

1. WHEN the source type is a constituent of the target union type (e.g., assigning `int` to `int | string`), THE Type_Checker SHALL treat the assignment as valid.
2. WHEN the source type is a union type and every constituent of the source is assignable to the target union type (e.g., assigning `int | string` to `int | string | bool`), THE Type_Checker SHALL treat the assignment as valid.
3. WHEN the source type is a union type and at least one constituent of the source is not assignable to the target type, THE Type_Checker SHALL emit a diagnostic error indicating which constituent types are not assignable.
4. WHEN the target type is not a union type and the source type is a union type, THE Type_Checker SHALL emit a diagnostic error indicating that a union type cannot be assigned to a non-union type without narrowing.
5. WHEN two union types have the same constituents regardless of order (e.g., `int | string` and `string | int`), THE Type_Checker SHALL treat them as the same type for assignability purposes.
6. WHEN a union type is used as a type argument and the type argument position expects a specific type, THE Type_Checker SHALL validate the union type against the expected type using the standard assignability rules.

### Requirement 7: Type Checking — Member Access on Union Types

**User Story:** As a Mist developer, I want to access members that are common to all constituent types of a union, so that I can use shared functionality without narrowing.

#### Acceptance Criteria

1. WHEN a member access is performed on a union-typed value and the member exists on ALL constituent types with compatible signatures, THE Type_Checker SHALL allow the access and resolve the result type as the union of the member's return types across all constituents.
2. WHEN a member access is performed on a union-typed value and the member does NOT exist on all constituent types, THE Type_Checker SHALL emit a diagnostic error indicating which constituent types lack the member.
3. WHEN a method call is performed on a union-typed value and the method exists on all constituent types with compatible parameter types, THE Type_Checker SHALL allow the call.

### Requirement 8: Type Checking — Pattern Matching with Union Types

**User Story:** As a Mist developer, I want to use pattern matching to narrow union types, so that I can safely work with the specific constituent type of a union value.

#### Acceptance Criteria

1. WHEN a type pattern is used on a union-typed scrutinee (e.g., `x is string s` where `x: int | string`), THE Type_Checker SHALL validate that the pattern type is one of the union's constituent types.
2. WHEN a type pattern matches a constituent of a union type, THE Semantic_Model_Builder SHALL introduce the pattern variable with the matched constituent type (not the union type).
3. WHEN a type pattern references a type that is not a constituent of the union, THE Type_Checker SHALL emit a diagnostic error indicating the pattern can never match, and the program is refused: a test no value of the union can pass is a mistake rather than dead code worth keeping, which is also C#'s judgment of an impossible pattern (CS8121, CS8510).
4. WHEN a `var` pattern is used on a union-typed scrutinee, THE Semantic_Model_Builder SHALL introduce the pattern variable with the full union type.

### Requirement 9: C# Emission — Helper Type Generation

**User Story:** As a Mist developer, I want the compiler to generate C# code that correctly represents union types at runtime, so that the compiled output preserves Mist's union type semantics even though C# lacks native union support.

#### Acceptance Criteria

1. THE Emitter SHALL generate a Helper_Type for each distinct union type used in the program, providing a discriminated container that can hold a value of any constituent type.
2. THE Helper_Type SHALL include a discriminator field (tag) that identifies which constituent type the current value belongs to.
3. THE Helper_Type SHALL include implicit conversion operators from each constituent type to the Helper_Type, so that assigning a constituent value to a union-typed variable compiles in C#. WHERE two constituents share one C# type (e.g., `int[3]` and `int[5]`, both `int[]`), an operator cannot tell them apart, so THE Helper_Type SHALL instead provide a named factory for each such constituent.
4. THE Helper_Type SHALL include a method or property to retrieve the stored value as a specific constituent type.
5. THE Emitter SHALL generate Helper_Types with unique names derived from the constituent types to avoid naming collisions.
6. THE Emitter SHALL reuse the same Helper_Type when the same union type (same constituents regardless of order) appears in multiple locations.

### Requirement 10: C# Emission — Union Type Usage

**User Story:** As a Mist developer, I want union-typed variables, parameters, and return types to be correctly emitted in C#, so that the transpiled code compiles and behaves as specified.

#### Acceptance Criteria

1. THE Emitter SHALL emit variable declarations with union types using the generated Helper_Type name (e.g., `Union_Int32_String x = 42;`).
2. THE Emitter SHALL emit method parameters with union types using the generated Helper_Type name.
3. THE Emitter SHALL emit method return types with union types using the generated Helper_Type name.
4. THE Emitter SHALL emit field declarations with union types using the generated Helper_Type name.
5. WHEN a constituent value is assigned to a union-typed variable, THE Emitter SHALL rely on the implicit conversion operator in the Helper_Type to perform the conversion, or, for a constituent sharing its C# type with another, SHALL call the factory of the constituent the value's type selects.
6. WHEN a union-typed value is used in a pattern match (`is` expression), THE Emitter SHALL emit C# code that checks the discriminator and extracts the typed value.

### Requirement 11: C# Emission — Pattern Matching on Union Types

**User Story:** As a Mist developer, I want pattern matching on union-typed values to be correctly emitted in C#, so that type narrowing works at runtime.

#### Acceptance Criteria

1. WHEN a Mist `is` expression with a type pattern is applied to a union-typed value, THE Emitter SHALL emit C# code that checks the Helper_Type's discriminator and extracts the value as the matched type.
2. WHEN a Mist `is` expression with a `var` pattern is applied to a union-typed value, THE Emitter SHALL emit C# code that binds the entire Helper_Type instance to the variable.
3. THE emitted C# pattern matching code SHALL produce the same boolean result as the Mist semantics specify (true when the runtime value matches the pattern type, false otherwise).

### Requirement 12: Error Diagnostics for Union Types

**User Story:** As a Mist developer, I want clear error messages when I misuse union types, so that I can quickly identify and fix problems.

#### Acceptance Criteria

1. WHEN a union type contains fewer than two distinct constituent types after deduplication and flattening, THE Compiler SHALL emit a diagnostic warning indicating that a union type requires at least two distinct types.
2. WHEN a member access is attempted on a union type and the member is not present on all constituents, THE Compiler SHALL emit a diagnostic error listing which constituent types lack the member.
3. WHEN a non-constituent type is assigned to a union-typed target, THE Compiler SHALL emit a diagnostic error naming the source type and the union type.
4. WHEN a union type is assigned to a non-union target without narrowing, THE Compiler SHALL emit a diagnostic error explaining that the union must be narrowed first.
5. WHEN a type pattern on a union-typed scrutinee references a type that is not a constituent, THE Compiler SHALL emit a diagnostic error indicating the pattern can never match, at the pattern's type, and SHALL refuse the program (criterion 8.3).
6. IF a constituent type reference in a union cannot be resolved, THEN THE Compiler SHALL emit a diagnostic error indicating the type is undefined.

### Requirement 13: Syntax Highlighting for Union Types

**User Story:** As a Mist developer using an editor, I want the `|` operator in type contexts to be syntax-highlighted, so that union type annotations are visually clear.

#### Acceptance Criteria

1. THE TextMate grammar (`mist.tmLanguage.json`) SHALL include a pattern that matches the `|` operator within type annotation contexts and assigns it the scope `keyword.operator.type.union.mist`.
2. WHEN a Mist source file contains a union type annotation (e.g., `int | string`), THE editor SHALL highlight the `|` operator distinctly from the logical OR operator `||`.

### Requirement 14: Feature Coverage Documentation Update

**User Story:** As a Mist project maintainer, I want the CSHARP_FEATURES.md document updated to reflect the newly implemented type union feature, so that the feature tracking document stays accurate.

#### Acceptance Criteria

1. WHEN the type unions feature is implemented, THE Compiler team SHALL update CSHARP_FEATURES.md to add a `Type Unions` entry marking it as implemented.
2. THE Compiler team SHALL update the `Summary` table at the bottom of CSHARP_FEATURES.md to reflect the new implementation counts.

### Requirement 15: Type Unions Sample Application

**User Story:** As a Mist developer evaluating the language, I want a sample application that demonstrates type unions in action, so that I can see how union types work with variables, parameters, pattern matching, and generics.

#### Acceptance Criteria

1. THE sample application SHALL be located in a new `Samples/TypeUnions/` directory following the existing sample app convention.
2. THE sample application SHALL demonstrate declaring variables with union types (e.g., `int | string value = 42;`).
3. THE sample application SHALL demonstrate method parameters with union types.
4. THE sample application SHALL demonstrate method return types with union types.
5. THE sample application SHALL demonstrate union types as type arguments (e.g., `List<int | string>`).
6. THE sample application SHALL demonstrate pattern matching to narrow a union-typed value to a specific constituent type.
7. THE sample application SHALL compile and run successfully through the Mist compiler pipeline, producing correct output via `Console.WriteLine`.
8. THE sample application SHALL expose a `public static void RunDemo()` method that exercises all demonstrated type union features and prints observable output.
9. THE `Samples/AllFeatures/mist.toml` SHALL be updated to add a `[[references]]` entry pointing to the TypeUnions sample project.
10. THE `Samples/AllFeatures/Program.mist` SHALL be updated to call `TypeUnions.Program.RunDemo()` from its `Main` method.
